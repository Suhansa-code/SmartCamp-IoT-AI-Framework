# Sri Lanka Resource Model — data provenance and method

SDRC-Box (Smart Camp Box) resource component. Predicts **daily food and
drinking-water requirements** for a Sri Lankan disaster-displacement camp, plus
a **7-day forecast** that accounts for expected registration growth or decline.

Shelter units and medical staffing were removed from scope and appear nowhere in
this pipeline as inputs, outputs, or intermediates.

---

## 1. Why the previous model was replaced

The earlier model trained on `data/processed/camp_features.csv`, a UNHCR-style
global dataset. Two problems, in order of severity.

**The targets were never measured.** All four target columns are closed-form
functions of `total_population`, verifiable against every one of the 2,251 rows:

| Target | Formula | Rows reproduced exactly |
|---|---|---|
| `food_kg_day` | `total_population × 0.6` | 2,251 / 2,251 (100 %) |
| `water_liters_day` | `total_population × 20` | 2,251 / 2,251 (100 %) |
| `shelter_units` | `total_population / 4.5` | 2,251 / 2,251 (100 %) |
| `medical_staff_needed` | `pop/500 + cr×pop×0.002 + er×pop×0.003` | 2,251 / 2,251 (100 %) |

So the dataset supplied a feature distribution, never labels. A regressor
trained on it learns to re-predict a linear function of its own input feature,
which is why the old model reported R² = 0.999986. That number measured
formula-fitting fidelity, not forecasting skill.

**The Sri Lankan coverage was not representative.** Sri Lanka contributes
**13 of 2,251 rows (0.58 %)**, and those rows are national conflict-displacement
caseloads from the post-civil-war period — 435,258 people in 2010 decaying to
9,528 by 2022. The deployment context is disaster shelters: median 55.5 people,
47 % of events under 50. That is a three-order-of-magnitude mismatch in scale
and a different displacement mechanism. Additionally, 60.6 % of rows in that
dataset carry global-median demographics, which put the elderly share at 3.0 %
against Sri Lanka's ~12 %.

## 2. Datasets in the current model

Every source below is Sri Lanka specific. Rejected datasets and the reasons are
in [`rejected/README.md`](rejected/README.md).

| Dataset | Granularity | Range | Role | Qualifies because |
|---|---|---|---|---|
| `subject_user.csv` + `consumption_user.csv` | per food item, per person, per 24 h recall day | 653 subjects, ages 6–14, 5 provinces, 2021 | Child food rate | `ADM0_NAME` is Sri Lanka for all 653 subjects; measured consumption, not a standard |
| `lka_idmc_idu_events.csv` | per displacement event | 78 events / 52 event IDs, 2025-01-13 → 2026-01-15 | Population scale and validation | IDMC/DMC reported Sri Lankan events; 100 % `displacement_type = Disaster` |
| `lka_faostat_food_balances.csv` | per (Item, Element, Year), national annual | 2010–2023 | **Corroboration only** | `Area` is Sri Lanka only. National per-capita supply is not a camp ration, so it is not a training target |
| `distribution.json` (production config) | per person per meal | current | Adult food rate, pregnancy top-up | The quantities `/api/distribute` actually issues in this system |

**On FAOSTAT specifically:** it is used to sanity-check, not to train. Sri Lankan
national food supply is 2,449–3,008 kcal/capita/day (2023: 2,675) against the
2,100 kcal/person/day humanitarian planning minimum. It confirms the camp
figures sit in a credible range; it cannot set them.

## 3. Rate table

Generated by `scripts/build_lka_rate_table.py` into
`models/lka_v2/ration_rates.json`. Every entry carries an `evidence` field.

| Rate | Value | Evidence | Source |
|---|---|---|---|
| Food, child (<18) | 1.76 kg/day | **measured** | Survey median, n = 653, ages 6–14 (mean 1.914, IQR 1.338–2.432) |
| Food, adult (18–59) | 1.60 kg/day | **production config** | `distribution.json`: breakfast 0.5 + lunch 0.6 + dinner 0.5 = three meals/day |
| Food, elderly (60–74) | 1.71 kg/day | **measured ratio** | adult × 1.066, BRIGHT Sri Lanka household survey, n = 4,229 |
| Food, elderly (75+) | 1.37 kg/day | **measured ratio** | adult × 0.855, BRIGHT Sri Lanka household survey, n = 1,214 |
| Food, elderly (blended) | 1.63 kg/day | **measured ratio** | used when a roster does not split 60–74 from 75+ |
| Food, pregnancy top-up | +0.60 kg/day | **production config** | `distribution.json` `pregnant_extra`, exact |
| Drinking water | 3.0 L/day | **humanitarian standard** | Sphere basic survival water: 2.5–3.0 L/person/day for drinking and food preparation; planning value is the upper bound |

As of schema 3 **no rate is an assumption.** The elderly figure was previously
`adult × 0.85`; it has been replaced by measured ratios from the BRIGHT Sri Lanka
household survey and split at age 75, because 60–74 year olds eat slightly *more*
than working-age adults (1.066×) while the over-75s eat less (0.855×) — a 25 %
difference a single elderly rate averages away. Every value carries its
`evidence` field inside the artifact, not only in this document.

### Known gaps, stated rather than hidden

1. The child rate is measured on **ages 6–14 only**. Ages 0–5 and 15–17 share the
   same `children_ratio` bucket but were never surveyed; a 4-year-old and a
   16-year-old are currently assigned the same rate.
2. The elderly *ratios* are measured, but the absolute values are those ratios
   applied to the production adult rate, because BRIGHT measures raw at-home
   food while the camp issues cooked weight.
3. **No Sri Lankan water consumption data exists.** `consumption_user.csv`'s
   `WATER_g` column is 100 % empty and the global water file has zero Sri Lanka
   rows, so water is entirely standards-based.
4. The pregnancy water top-up is **not applied**. `distribution.json` specifies
   +2 L, but that was defined against the 15 L domestic basis and does not
   transfer to a 3 L drinking basis without a source.

### Water: drinking vs domestic

This model reports **3 L/person/day**, the Sphere *survival drinking and food
preparation* requirement. The production `distribution.json` issues **15 L**,
which is the Sphere *basic domestic supply* figure covering drinking, cooking and
hygiene.

**These are different quantities and the model deliberately reports the narrower
one.** The 3 L figure is the defensible survival minimum; the 15 L figure is what
the camp actually distributes. Anyone comparing the model's water output against
`/api/distribute` issuance will see a 5× gap, and that gap is intentional, not a
defect. If the operational planning figure is wanted instead, change
`water_drinking.value` in the rate table to 15.0 and re-run the build script.

## 4. Method

### 4a. Daily ration — deterministic, not ML

```
food_kg_day      = children × 1.76 + adults × 1.60 + elderly × 1.36
                   + pregnant × 0.60
water_liters_day = population × 3.0
```

This is a rule, not a model, and that is deliberate. The per-person quantity is a
policy constant that the platform already issues; there is no measured variation
in camp consumption anywhere in the repository to learn from. Fitting a regressor
to it is exactly what produced the R² ≈ 1 artifact in the previous version.
Applying a constant as a constant is honest and auditable — and it can be swapped
for a fitted model the day real consumption records exist, without changing the
calling interface.

### 4b. Seven-day forecast — the actual statistical component

The uncertainty in this problem is not "how much does one person eat", it is "how
many people will be here on Thursday". That is where the model sits.

`src/population_forecast.py` fits a **Theil–Sen** trend to the cumulative
registration history and projects the population forward, then applies the
ration rule to each projected day.

Theil–Sen takes the median of all pairwise slopes rather than minimising squared
error. Disaster intake arrives in bursts, and a single mass-arrival day would
drag an ordinary least-squares line badly. Tested against a synthetic 10-day
series containing a 400-person spike, Theil–Sen recovered +8.5 persons/day
against an underlying trend of ~8.3.

**The trend is fitted on the last 7 days, not the whole history.** A camp's
record contains its intake ramp — a steep rise from zero over the first days.
Theil-Sen medians *all* pairwise slopes, so once the camp starts emptying those
ramp pairs keep dragging the fitted slope upward and the forecast projects growth
for a camp that is demobilising. Measured over 60 heterogeneous synthetic camps
(`data/scenarios`, four trajectory archetypes with per-camp decay rates):

| Trend window | MAE h=7 | MAPE h=7 | Bias h=7 |
|---|---|---|---|
| entire history | 53.07 | 64.6 % | +34.28 |
| 10 days | 49.74 | 59.2 % | +30.84 |
| **7 days (shipped)** | **47.33** | **55.0 %** | **+28.10** |
| 5 days | 44.73 | 51.3 % | +24.95 |

Shorter windows score better still; 7 is chosen to match `MIN_DAYS_FOR_BAND`,
since the residual band needs that many points to mean anything. The confidence
tier is still judged on the *entire* history — the window changes what is fitted,
not how much data the model claims to have. On the intake-only back-test the same
change improved h=7 MAE from 2,023.6 to 1,763.4, so it does not trade one regime
for the other.

Estimator selection is driven by how much history exists, and the output says so:

| Observations | Method | Confidence | Behaviour |
|---|---|---|---|
| < 3 days | `flat_hold` | LOW | Population held flat. Labelled a cold-start fallback, **not** presented as a fit |
| 3–6 days | `theil_sen` | MEDIUM | Trend fitted, no uncertainty band |
| ≥ 7 days | `theil_sen_with_band` | HIGH | Trend plus a band from the median absolute residual, widening with horizon |

Growth is capped at 3× the current headcount across the horizon, and population
cannot go negative, so a declining camp projects down without crossing zero.

**This matters materially.** For a camp rising from 40 to 205 residents over a
week, the trend-aware 7-day food total is 2,875 kg against 2,330 kg for flat
headcount × 7 — a **23 % difference**, which is the gap between a supplied camp
and a short one. (An undamped trend would have said 3,264 kg. The back-test
below shows why that figure was too high.)

Demographic ratios are held constant across the horizon. Nothing in the
repository shows camp composition shifting predictably during an event, so
projecting a change would be invention.

### Back-test: does the trend actually beat doing nothing?

`scripts/backtest_forecast.py` runs a rolling-origin evaluation. For each camp
history of N days and each origin t, it fits on days 0..t and predicts
t+1..t+7, so every prediction uses only data available when it would have been
made. Errors are aggregated per horizon step.

The camps come from `scripts/generate_camp_registrations.py`. Their daily curves
are synthetic, but their **scale and onset speed are not**: camp sizes are
bootstrapped from the 78 real IDMC event figures and the hazard mix and onset
durations come from the same file.

The baseline to beat is `flat` — tomorrow equals today. That is what a planner
does with no model at all, so beating it is the minimum bar.

200 camps x 21 days, 6 % noise, error at h=7:

| Method | MAE | MAPE | Bias |
|---|---|---|---|
| **Theil-Sen, damped (shipped)** | **2,023.6** | **30.7 %** | −1,115.8 |
| Theil-Sen, undamped | 2,882.7 | 50.1 % | +652.7 |
| OLS | 3,096.1 | 53.8 % | +949.5 |
| flat (no model) | 2,748.3 | 38.7 % | −2,748.3 |

**This back-test found a real defect.** The undamped estimator — the original
design — *loses to the flat baseline*: MAE 2,882.7 against 2,748.3. The bias
column shows why. Camp intake saturates; people arrive fast and then stop. A
slope fitted on the steep middle of that curve keeps growing after arrivals have
ceased, so the projection overshoots (+652.7 at h=7) by more than doing nothing
undershoots in MAPE terms.

The fix is a damped trend: each day ahead contributes `phi^i` of the fitted
slope, so the projection flattens as it extends. Sweeping phi:

| phi | MAE h=7 | MAPE h=7 | Bias h=7 |
|---|---|---|---|
| 1.00 (undamped) | 3,061.0 | 53.9 % | +866.7 |
| 0.90 | 2,408.9 | 39.5 % | −323.5 |
| **0.80 (shipped)** | **2,023.7** | **30.9 %** | −1,115.8 |
| 0.70 | 1,906.4 | 27.6 % | −1,642.5 |

0.7 minimises MAE but under-orders most, and under-provisioning means a camp
runs short — the costlier error. 0.8 is the operating point, and `TREND_DAMPING`
is a single constant in both implementations.

With damping the shipped model beats both baselines at every horizon, and is
near-unbiased at h=1 (+31.3) and h=2 (−18.8). Under mass-arrival bursts it holds
its margin over flat (+25.3 %) while OLS collapses (Theil-Sen is 53.5 % better
than OLS there, against 34.6 % without bursts) — which is the robustness claim
the estimator was chosen for, now measured rather than asserted.

**What this does and does not establish.** It establishes that the estimator
recovers a trend from data with known properties, degrades predictably with
horizon, and resists bursts. It does **not** establish field accuracy: the daily
curves are generated. Report it as estimator validation, never as forecast
accuracy in a real camp.

### An honest limitation on the forecast

**There is no historical registration data in this repository to validate the
forecaster against.** `camp.db` holds 5 persons and 3 check-ins across 3 distinct
days, and only 5 of 52 IDMC events report more than one date — the single
multi-point trajectory, Cyclone Ditwah, spans 7 observations over 43 days, not
daily. The forecaster is therefore built to fit on live check-in history as it
accumulates in deployment, and its accuracy is currently **unvalidated**. The
confidence tier it reports describes how much data it had, not how accurate it
proved to be. Validating it requires operating a camp and recording daily
registration counts.

## 6. Running it

```bash
cd cloud-platform/prediction-models

# Rebuild the rate table from the Sri Lanka sources
.venv/bin/python scripts/build_lka_rate_table.py

# Self-test the forecaster (cold start, steady intake, spike rejection)
.venv/bin/python src/population_forecast.py

# Self-test the predictor at real Sri Lankan event scales
PYTHONPATH=src .venv/bin/python src/lka_resource_predictor.py
```

```python
from datetime import date, timedelta
from lka_resource_predictor import LkaResourcePredictor

predictor = LkaResourcePredictor()

# Today
predictor.daily_requirement(total_population=320, children=96,
                            elderly=38, pregnant=4)

# Next seven days, from observed registration history
start   = date(2026, 8, 15)
history = [(start + timedelta(days=i), p)
           for i, p in enumerate([40, 66, 95, 118, 150, 171, 205])]

plan = predictor.forecast(history=history, children_ratio=0.28,
                          elderly_ratio=0.12, pregnant=3)
print(predictor.summary(plan))
print(predictor.provenance())    # for the report
```
